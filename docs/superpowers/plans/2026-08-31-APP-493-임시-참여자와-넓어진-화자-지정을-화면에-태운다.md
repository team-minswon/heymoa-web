## 1. 계약을 어떻게 갈아탔나

`openapi3.yml` 은 **server 정본에서 `/internal/**` 을 뺀 것**입니다. 이번에는 dev 쪽도 그 사이
움직여서, 통째로 덮으면 남의 델타가 사라집니다. **3자 비교로 이쪽 델타만 얹었습니다** — base
(브랜치가 갈라진 지점)와 비교해 PRO-41 이 더한 것만 뽑고, dev 의 최신 위에 텍스트째 splice.

**재덤프하지 않았습니다.** 생성기를 다시 돌리면 스키마 순서가 밀려, 내용이 같은데도 수천 줄
diff 가 나고 다음 병합이 같은 충돌을 냅니다. 실제로 docs 계약 미러에서 그 일이 났습니다.

그 위에서 `pnpm orval` 이 모델 24개를 만들었습니다. 손으로 만진 생성 파일은 없습니다.

**`guestIds` 가 `(object|boolean|string|number)[]` 로 생성됩니다.** 스칼라 배열 항목 타입이
안 붙는 기존 결함(APP-342)이고 PRO-41 이 두 번째 사례를 더했습니다. 이 브랜치에서 안 고쳤습니다.

## 2. 참석자 필드 — 이 작업에서 가장 오래 걸린 자리

`note-participants-field.tsx` 가 543줄 바뀌었습니다. 기능은 단순한데 **판정이 어렵습니다.**

### 「＋ 추가」를 언제 보여주나

정확히 같은 이름의 후보가 있으면 안 보여줍니다. 그런데 **후보를 아직 못 불러왔을 때**도 안
보여줘야 합니다 — 안 그러면 이미 있는 사람을 하나 더 만듭니다.

판정을 두 개로 갈랐습니다. 하나로 두면 반드시 한쪽이 틀립니다.

```tsx
// 그릴 수 있나 — 후보를 손에 들었나
const candidatesLoaded =
  members.length > 0 && guestsData?.status === 200 && guestsData.data.success;

// 만들어도 되나 — 위에 더해, 지금 이 순간이 최신인가
const candidateSourcesReady =
  Boolean(workspaceId) && candidatesLoaded &&
  !membersPending && !membersFailed && !guestsPending && !guestsFailed && !candidatesRefetching;
```

**하나로 뭉쳤다가 회의에서 나간 참여자가 안 그려졌습니다.** 「그릴 수 있나」에 「최신인가」를
섞으면, 재조회 중에 이미 손에 든 목록까지 안 그립니다.

### 저장 중에 남의 변경을 덮는 문제

참여자 저장이 **전체 교체 API** 입니다. 사람이 체크박스를 만지는 동안 다른 사람이 참여자를
바꾸면, 내가 든 옛 목록을 통째로 보내 그 변경을 지웁니다.

3자 병합으로 흉내 냈습니다 — **내가 끈 것만 끄고 나머지는 최신을 따릅니다.**

```tsx
function mergeDraft(next: string[], base: string[], current: string[]) {
  const turnedOff = base.filter((key) => !next.includes(key));
  const merged = new Set(next);
  for (const key of current) { if (!turnedOff.includes(key)) merged.add(key); }
  return [...merged];
}
```

`base` 는 **초안을 열 때의 저장값**입니다. 토글로 열든 「＋ 추가」로 만들다 열든 **양쪽에서
찍습니다** — 한쪽을 빠뜨렸다가, 만들기로 시작한 초안이 base 없이 병합돼 남의 참여자를
지웠습니다.

**최신에서 출발해 내 델타만 얹습니다.** `next`(스냅샷)에서 출발하면 그 안에 `base` 시절
사람이 그대로 있어, 그 사이 남이 **뺀** 사람까지 되살아납니다 — 그의 화자 연결은 이미
지워졌으므로 **이름만 돌아오고 연결은 안 돌아옵니다.** 양쪽 방향 모두 테스트가 있습니다.

> **이 창은 완전히 안 닫힙니다.** 전체 교체 API 위에서 낙관적 병합을 흉내 내는 것이라,
> 요청이 날아가는 순간과 서버가 받는 순간 사이는 못 봅니다. **구조적 한계라 여기서는 창을
> 좁히는 데까지만 갔습니다.** 닫으려면 서버가 부분 갱신이나 버전 토큰을 받아야 합니다.

## 3. 화자 지정 메뉴

Combobox 를 그대로 두고 **맨 아래에 라디오 두 줄**만 얹었습니다. 검색·「＋ 추가」·「이름 안
붙임」 전부 살아 있습니다. 하단 버튼이 범위를 따라 바뀝니다.

| 라디오 | 하단 버튼 |
|---|---|
| 이 화자의 모든 발화에 적용 (기본) | 「이름 안 붙임」 |
| 현재 발화에만 적용 | 「개별 지정 해제」 (개별 지정이 있을 때만 활성) |

**메뉴를 닫으면 범위가 기본으로 돌아갑니다.** 남겨 두면 다음에 다른 화자를 누른 사람이 「모든
발화」인 줄 알고 한 줄만 바꿉니다 — 라디오는 화면 아래라 눈에 안 들어옵니다.

### 덮기 전에 건수를 말한다

「모든 발화에 적용」이 그 라벨의 개별 지정을 지웁니다. 누르기 **전에** 몇 줄이 덮이는지 말하고
취소할 길을 줍니다. 건수는 **이미 손에 든 발화 목록에서** 세므로 서버에 안 묻습니다.

세는 함수가 `number | null` 을 돌려줍니다 — **`null` 은 「0」이 아니라 「확인 못 했다」** 이고,
그때는 확인 창을 띄웁니다. 못 셌다는 이유로 조용히 지나가면 사람이 모르는 채로 덮습니다.

### 후보가 셋에서 온다

이 회의의 참여자 + 워크스페이스 멤버 전원 + 이 회의 밖의 임시 참여자. 마지막 갈래를 안 열면
사람이 **같은 이름을 하나 더** 만듭니다. 아직 참여자가 아닌 멤버는 계정으로 가리켜 보내고,
서버가 참여자로 넣습니다.

지정에 성공하면 **전사와 노트를 함께 다시 읽습니다.** 참여자가 늘 수 있어 노트만 옛 목록으로
남으면 회의 정보의 체크가 안 켜집니다.

## 4. 설정 — 임시 참여자와 연동

`workspace-guests-settings.tsx` 가 이번에 새로 생긴 유일한 화면입니다. 설정 › 멤버에 **별도
자리**로 붙습니다 — 멤버 목록·역할 변경·내보내기와 안 섞습니다.

목록은 멤버 전원에게, **「연동」과 「삭제」는 ADMIN 에게만** 보입니다. 연동은 미리보기를 먼저
띄우고 **되돌릴 수 없다는 사실**을 함께 말합니다.

**「못 불러온 것」과 「없는 것」을 가릅니다.** 뭉치면 조회가 실패했을 때 「임시 참여자가
없습니다」가 떠서, 사람이 목록이 빈 줄 알고 같은 이름을 다시 만듭니다.

## 5. 한글 조합(IME)

`@base-ui/react` 의 Combobox 는 **조합 중에 controlled 값을 일부러 안 올립니다** — 옵션이 조기에
걸러져 `Empty` 가 잘못 뜨는 것을 막으려는 것이고, **거르기에는 그 판단이 맞습니다.**

문제는 **이름을 짓는 자리가 이번에 처음 생겼다**는 것입니다. 「이민형」을 치면 마지막 「형」이
조합 중이라 버튼이 「＋ "이민" 추가」로 뜨고, **실제로 「이민」이 만들어집니다.**

거르기는 그대로 두고 **이름을 짓는 자리만** 사람이 친 그대로의 값을 보게 했습니다 —
`ComboboxInput` 에 `onTypedValueChange` 를 달아 `onInput` 에서 DOM 값을 넘깁니다. controlled
값에 **되쓰지 않으므로** 조합을 안 깨뜨립니다.

**공용 컴포넌트 한 곳에서 고쳤습니다.** 호출부는 둘(참석자 필드 · 화자 드롭다운)이고, 화면마다
따로 고치면 다음에 같은 입력을 쓰는 세 번째 화면이 또 틀립니다.

**e2e 가 값을 냈습니다.** 이 기능은 화면 셋과 목 DB 가 함께 맞아야 성립해서, 단위 테스트가
전부 통과해도 엮이는 자리에서 깨집니다. 「임시 참여자를 계정과 잇고 화자 지정을 지킨다」는
설정 화면의 마운트부터 전사의 화자 칩까지를 한 줄로 꿰고, 「한 사람을 화자 둘에 붙여도 앞이
안 떨어진다」와 「라벨 전체 적용 전에 경고한다」는 목과 서버가 갈라지면 곧바로 깨집니다.

**거울 테스트는 안 만들었습니다.** 목 DB(`lib/mocks/db.ts`)가 서버와 같은 규칙을 흉내 내는
것이 이 레포 검증의 바닥인데, 그 목을 목으로 검증하면 아무것도 보증하지 않습니다.

### 안 한 것

**동시성 IT.** server 쪽에서 락 순서를 검증하는 IT 를 썼다가 지웠습니다 — 순서를 되돌려도
통과해서, 「실패할 수 없는 테스트」였습니다. 마이크로초 단위 인터리빙이 필요합니다.

**3자 병합의 남은 창.** 위 §2 의 구조적 한계라 테스트로 못 막습니다.

**연동 미리보기가 실패했을 때 후보를 다시 읽지 않습니다.** 창을 연 뒤 남이 대상 멤버를
내보내면 미리보기가 `WORKSPACE_MEMBER_NOT_FOUND` 로 실패하는데, `catch` 가 고른 대상만
비우고 **제거된 멤버를 후보에 그대로 둡니다.** 같은 사람을 다시 눌러도 같은 오류가 반복되고,
창을 닫았다 열기 전에는 안 풀립니다. 오류 코드를 보고 멤버 쿼리를 다시 읽는 것이 답인데,
**동시 편집의 꼬리를 하나 더 무는 자리**라 여기서 끊었습니다.

**`confirmedWorkspaceId` 의 실패 경로.** 소속 조회가 끝내 실패하면 그 값이 `undefined` 로
남아 후보 조회가 **영원히 로딩**입니다. 이 메커니즘은 dev 것(회의 시작 버튼)이고 PRO-41 이
쓰는 자리를 늘리면서 **보이게 됐을 뿐**이라, 여기서 반만 고치지 않습니다 — 오류 상태를
`note-panel` 에서 두 화면으로 내리는 일이고 PRO-41 밖입니다.

## 7. 남은 것

- **`200 success:false` 를 transport 에서 정규화**하고 그 위에서 화면 판정을 통일하는 것.
  `fetcher` 가 이 봉투를 실패로 안 바꿔서 `isError` 가 `false` 이고 `data` 가 들어 있습니다 —
  화면이 무슨 네트워크 상태 검사를 해도 **전부 우회됩니다.** 앱 전체 문제라 PRO-41 밖의 별도
  이슈로 두고, **경계를 코드 주석에 박아 뒀습니다**(`workspace-guests-settings.tsx`).
  「고쳤다고 표시된 채 안 고쳐진」 자리를 안 남기려는 것입니다
- **`confirmedWorkspaceId` 의 오류 상태** — 위 §6 참조. dev 의 메커니즘이라 별도 이슈입니다
- **APP-342** — 스칼라 배열 항목 타입. PRO-41 이 두 번째 사례를 더했습니다
- **APP-496** — 응답의 `assignedUserId` 제거. 이 화면이 **배포되어 안정된 뒤**입니다
