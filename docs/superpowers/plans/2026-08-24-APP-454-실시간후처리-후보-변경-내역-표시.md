# APP-454 실시간·후처리 후보 변경 내역 표시 Implementation Plan

**Goal:** 회의 중 맥락 후보를 노트 오른쪽 레일에 시간순 사건 목록으로 보이고, 근거·공백·연결
상태를 계약이 싣는 값으로만 그린다.

**Spec:** docs `projects/PRO-33-회의-중-맥락-연결/spec/APP-454/spec.md`
(로컬 브랜치 `docs/app-454/context-rail` @ `621f293`. **아직 push하지 않았고 PR도 없다.**
docs origin/main에 올라간 뒤 ref를 이 줄에 고정한다.)

**Architecture:** 계약은 아직 `openapi3.yml`에 없다. `lib/notes/context-candidates/`에 draft
zod 스키마를 한곳에 격리하고 REST 목과 WS 목이 같은 스키마를 쓴다. 계약이 도착하면 그 파일만
orval 산출물로 갈아 끼운다. 상태는 기존 실시간 4계층을 그대로 따른다 — transport는 기존 note
topic, protocol은 feature별 zod, reducer는 순수 함수, provider가 Query 캐시와 잇는다.

**Tech Stack:** Next.js 16 App Router · TanStack Query · zod · MSW · vitest · Playwright

---

## Global Constraints

- **계약 draft는 한 파일에만 둔다.** `lib/notes/context-candidates/contract.ts`. 화면 코드도
  MSW도 여기서만 타입을 가져온다. 계약이 오면 이 파일이 orval 재수출로 바뀐다.
- **`z.strictObject`를 쓴다.** 기존 `note-topic-protocol.ts`와 같은 엄격도다. server가 확정한
  required 필드를 빠짐없이 선언한다.
- **`runKey`에 TSID 스키마를 쓰지 않는다.** 계약이 `^[A-Za-z0-9_-]{1,64}$`이다. APP-466 구현이
  지금은 `new_tsid`로 발급해 13자리처럼 보이지만 그걸 보고 좁히면 안 된다.
- **`operation`에서 `status`를 유도하지 않는다.** 실린 `status`·`closeReason`을 읽는다.
  `operation=RESOLVE` 하나가 CLOSED 하나와 OPEN 1~3개를 동시에 만든다.
- 낙관적 갱신을 만들지 않는다. 서버 확정 event만 소비한다.
- 폴링 루프를 만들지 않는다. 필요하면 TanStack Query의 `refetchInterval` + `enabled`만 쓴다.
- 「요약」·「총 N건」·완결 어휘를 이 표면에 쓰지 않는다.
- `lib/api/generated/`와 `middleware.ts`는 건드리지 않는다(hook이 막는다).
- Linear·원격·docs PR은 이 실행 범위에서 건드리지 않는다.

## 확정된 wire 계약 (server 추가 답변 3·4)

```ts
type ContextCandidateHead = {
  candidateId: string            // 13 TSID
  revision: number
  operation: "CREATE" | "AMEND" | "CORRECT" | "RETRACT" | "RESOLVE"
  kind: "AGENDA" | "DECISION" | "ACTION_ITEM" | "ISSUE" | "QUESTION"
      | "STATUS_REPORT" | "INSIGHT"
  status: "OPEN" | "CLOSED"
  closeReason: "RETRACTED" | "RESOLVED" | null
  revisionSource: "LIVE" | "POSTPROCESS"     // v1 생산값은 LIVE뿐
  content: string                             // 1~500 code points
  createdSequence: number
  lastEvidenceSequence: number
  aiSemanticRevisionCount: number             // 저장값. revision-1로 계산하지 않는다
  resolvesCandidateId: string | null
  evidence: Array<{
    segmentId: string; sequence: number; startedAtMs: number; text: string
    role: "SUPPORTS" | "REFUTES" | "CONDITIONS" | "RETRACTS" | "REFERENCES"
  }>
}

type AppliedRange = {
  runKey: string                              // opaque 1~64
  applyStatus: "APPLIED" | "PARTIAL_RECORDED"
  fromSequence: number; toSequence: number
  fromStartedAtMs: number; toEndedAtMs: number
  rawDeltaSaturated: boolean; semanticUnitSaturated: boolean
  appliedAt: string
}

// GET /v1/notes/{noteId}/context-candidates
//   → { candidates: ContextCandidateHead[], appliedRanges: AppliedRange[] }
// GET /v1/notes/{noteId}/context-candidates/{candidateId}/revisions
//   → { candidateId, revisions: ContextCandidateHead[] }

// /topic/notes/{noteId}
// { type: "context.candidate.changed", eventId, occurredAt, candidate }
// { type: "context.classification.batch.applied", eventId, occurredAt, coverage: AppliedRange }
```

전달 보장은 **best-effort WebSocket + REST recovery**다. 유실이 가능하다.

## 실행 후 남는 것

- **계약이 `openapi3.yml`에 없다.** `contract.ts`는 draft이고 server의 APP-459가 머지되면
  교체해야 한다. server는 APP-453 선행 결함(512-token invariant, outbox self-contained payload,
  status 행렬, OpenAPI oneOf) 뒤로 밀려 있다
- **후처리 diff를 구현하지 않는다.** APP-458 spec이 없다. `revisionSource`만 파서가 받는다
- **신판 토큰이 web에 없다.** `m-evidence`·`m-warn-*`·`m-control`과 Geist Mono가 없어 현재
  `--el-*`로 근사한다. PRO-18과의 순서는 spec의 열린 질문이다
- **F3(충돌)·F5(사람 개입)는 v1 밖이다.** PRO-34/PRO-36
- **docs spec이 push되지 않았다.** 로컬 브랜치 `docs/app-454/context-rail`에만 있다
