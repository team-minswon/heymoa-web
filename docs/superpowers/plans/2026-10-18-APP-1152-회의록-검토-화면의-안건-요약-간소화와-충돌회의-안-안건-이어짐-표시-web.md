관계의 백그라운드 재조회 안내 깜박임, 최신 flow 조회 실패를 대기로 표시하는 문제와 그래프 zoom의 렌더 중 상태 갱신 경고도 수정했습니다. nullable 표본 검사는 선택 필드의 생략만 null로 세고 필수 필드의 생략은 null 표본으로 세지 않습니다.

Mock의 새 APPLIED 허용은 실제 서버의 호환 처리와 같으므로 유지합니다. 새 AI 안건은 description 빈 배열을 사용하고 옛 결과는 설명 전문을 보존합니다. 안건 연결은 source=current, target=previous 계약이므로 그래프가 target에서 source로 향합니다. 알 수 없는 관계 종류는 유추하지 않습니다. NOT_REQUESTED의 안건 폴링은 자동 분석 진입·늦은 결과를 받기 위한 대기 상태 갱신으로 유지합니다. 미분류 새 명제 뒤에는 이전 안건이 계속 논의 중이라고 추정하지 않습니다.

전체 브라우저 테스트 114개를 한 번에 통과했습니다. 이후 보완에는 전체 단위 검사와 관련 브라우저 테스트 9개를 다시 통과했습니다. 중단한 Playwright 실행이 남긴 임시 trace가 ESLint에 잡힌 실행은 통과로 세지 않고, 완료 뒤 임시 산출물을 정리한 상태에서 verify를 다시 통과했습니다.

충돌 복구는 저장 중 비활성화된 검토 쿼리도 `fetchQuery`로 직접 읽고 새 판을 받을 때까지 잠금을 유지합니다. 복구 조회가 실패하면 입력을 남기고 재시도를 안내하며 성공했다고 표시하지 않습니다. 업무 목록은 진입과 늦은 분석 결과 반영 때 다시 읽습니다. 기대 판보다 캐시 판이 낮으면 조회 중에 변경 충돌로 표시하거나 넘기기를 강요하지 않습니다. 느린 충돌 복구·실패 후 재시도·최근 캐시보다 높은 유효한 제안의 회귀 검사를 추가했습니다.

관계 대상 이동에는 실제 검토 행과 상세 패널만 스크롤 대상으로 표시합니다. 같은 항목 ID를 가진 그래프의 숨김 접근성 버튼을 선택하지 않습니다. 단위 검사에서 실제 패널의 `scrollIntoView` 호출을 확인했고, 공개 Mock 브라우저에서도 이슈 관계 대상 클릭→그래프 전환→실제 DIV 패널이 화면 안에 들어오는 것을 확인했습니다. 마지막 스크롤 보완 후 전체 단위 2,603개와 lint·타입·build, 관련 E2E 15개를 통과했습니다. 전체 E2E 115개는 직전 복구 실패 보완 코드에서 통과했으며, 마지막 보완의 영향 범위는 이 관련 묶음으로 다시 확인했습니다.


늦은 분석 완료 뒤 검토본·요약·스크립트·관계를 다시 읽을 때는 조회 실패가 resolve되는 기본 동작을 사용하지 않습니다. 필수 조회가 모두 성공한 경우에만 해당 흐름을 갱신 완료로 기록합니다. 실패하면 이전 내용과 초안을 보존하고 재시도 안내를 표시하며 검토 완료를 막습니다. 같은 흐름의 폴링은 실패를 지우지 않고, 새 흐름이나 사용자가 누른 재시도에서 다시 읽습니다. 업무 목록 실패는 기대 판과 캐시를 대조하는 기존 제안별 상태로 처리합니다.

최신 기반 전체 단위 220파일/2718개와 lint·타입·production build를 통과했습니다. 병렬 부하에서 승인 경로가 기본 5초 제한을 넘은 자료는 보존하고 상한을 바꾸지 않은 채 maxWorkers=2로 확인했습니다. 새 검사 트리의 404는 dev 서버 종료와 캐시 정리가 끝난 뒤 노트 주소 HTTP200부터 확인했습니다. 설정 창이 현재 주소를 기록하므로 임시 참여자 연동 검사는 노트 닫기의 경로 이동이 완료된 뒤 설정을 열도록 맞췄습니다. 새로고침 없이 연동한 화자가 유지되는 기존 단언은 그대로입니다. 해당 검사는 3회 연속 통과했고 전체 브라우저 122개도 3.7분에 모두 통과했습니다.

## 실제 서버 연결 검증 준비

환경과 비용 답변 및 서버·AI 준비 확인 전에는 아래 Web 서버나 pair stack을 띄우지 않습니다. 실행은 별도 QA 계정과 삭제 가능한 QA 워크스페이스에서 합니다. 기본 playwright.config.ts와 e2e/meeting-review.spec.ts는 MSW 시드를 사용하므로 실제 서버 검증의 근거로 사용하지 않습니다.

### 실행 입력과 인증

서버 소유자가 /tmp/app-1152-real-review-input.json에 다음 비밀이 아닌 값을 확정합니다. 실제 ID·판·값은 seed 생성 뒤 GET 응답에서 읽고 임의의 Mock ID로 대체하지 않습니다.

- webBaseUrl, apiBaseUrl, workspaceId, projectId, reviewerUserId.
- apply: noteId, reviewId, reviewVersion, itemId, targetTaskId, expectedRevision, rowContent, draftDue, draftAssignee(type/id/label 참조), draftStatus.
- conflict: 별도 noteId·reviewId·itemId·targetTaskId·expectedRevision와 경합 actorUserId.
- duplicate(별도 확인 시): 같은 taskId를 대상으로 한 두 included 검토 항목의 itemId.

검토·승인 권한을 가진 회의 시작자/관리자 테스트 계정을 사용하고 서버의 공개 권한 계약으로 허용됨을 먼저 확인합니다. 회의는 종료되어 있고 필요한 분석 자료의 상태가 SUCCEEDED여야 합니다. 목표 업무와 검토 항목은 같은 QA 프로젝트에 속하며 정상 시드는 대상 업무 revision과 초안 expectedRevision이 같아야 합니다. 초안은 기한 등 최소 한 필드가 원본 업무와 다르게 준비합니다. 정상 시드에는 기존 업무 변경 제안 1개만 두거나, 나머지 제안의 선택을 확정해 검토 완료를 막지 않게 합니다. 검토 항목은 included=true, taskChanges decision=null·draft=null, 회의는 미승인 상태여야 합니다. 각 시나리오는 승인 전 상태의 별도 노트를 씁니다.

인증은 해당 환경에서 승인한 QA OAuth 로그인 또는 서버 소유자가 준비한 테스트 세션으로 합니다. HttpOnly 쿠키를 콘솔에 복사하지 않습니다. 인증을 재사용할 때는 Playwright storageState를 /tmp의 비공개 파일로 저장하고 그 경로만 공유합니다. 파일은 Git·문서·로그에 넣지 않습니다. headless 실행은 동일 환경에서 생성한 인증 상태를 BrowserContext에 불러옵니다.

### 브라우저 실행 방법

실제 서버를 가리키는 별도 Web을 4100에서 실행합니다. QA_API_BASE_URL과 QA_WEB_BASE_URL은 확정된 target의 값이며 앱이 실제 읽는 변수로 전달합니다. 기존 Mock 8080은 보존합니다.

```sh
NEXT_PUBLIC_API_MOCKING=disabled NEXT_PUBLIC_API_BASE_URL="$QA_API_BASE_URL" NEXT_PUBLIC_SITE_URL="$QA_WEB_BASE_URL" pnpm dev --hostname 0.0.0.0 --port 4100
```

GUI 사용이 가능한 검사 기기에서는 다음 명령으로 QA 로그인과 인증 상태 저장을 진행합니다. 이미 서버 소유자가 준비한 storageState가 있으면 저장 단계를 생략합니다.

```sh
pnpm exec playwright codegen --save-storage="$QA_STORAGE_STATE" "$QA_WEB_BASE_URL"
pnpm exec playwright open --load-storage="$QA_STORAGE_STATE" "$QA_WEB_BASE_URL/w/$QA_WORKSPACE_ID/notes/$QA_APPLY_NOTE_ID?view=full&tab=summary"
```

headless 자동화에서는 @playwright/test의 chromium.launch()로 만든 browser의 newContext({ storageState: process.env.QA_STORAGE_STATE })에 해당 상태를 읽고 같은 주소를 엽니다. 실제 응답은 page.evaluate의 fetch(url, { credentials: 'include' })로 읽습니다. 외부 API origin을 사용할 때는 서버 CORS·쿠키 정책이 해당 Web origin을 허용해야 합니다. Web을 여는 것만으로 AI 분석을 재요청하지 않고, 이미 준비된 분석·검토 seed를 사용합니다. 실제 모델 호출은 서버·AI 소유자가 비용 조건에 따라 별도로 실행합니다.

### 확인 순서와 합격 기준

1. 브라우저에서 ServiceWorker MSW가 이 origin을 제어하지 않고 /v1/auth/session이 QA 사용자로 인증됨을 확인합니다. 검토 GET과 /v1/workspaces/{workspaceId}/projects/{projectId}/tasks GET으로 검토본 및 대상 업무의 status·assignee·due·revision을 기록합니다. 민감한 인증 헤더는 기록하지 않습니다.
2. 해당 itemId 행의 ‘기존 할 일에 반영할지’에서 반영을 고릅니다. 기한과 담당 초안을 편집하고 검토 PATCH가 decision=APPLY, targetId=targetTaskId, taskChange.expectedRevision 및 담당 type/id/label을 그대로 저장하는지 확인합니다. 새로고침 뒤 GET taskChanges[].draft와 ‘반영 예정’이 복원되어야 합니다. 원본 제안 필드와 저장 초안은 별개여야 합니다.
3. 넘기기→반영을 바꾸고 매번 GET으로 KEEP/APPLY와 기존 초안 보존을 확인합니다. 승인 전 대상 업무의 status·assignee·due·revision이 최초 값과 같고 브라우저에서 대상 업무 PUT이 0건이어야 합니다.
4. 검토 완료 확인창의 기존 업무 변경 수를 확인하고 실제 승인 POST를 한 번 보냅니다. 성공 뒤 확정 상태·반영됨을 확인합니다. 대상 업무는 저장한 초안 값이며 revision이 정확히 한 번 증가해야 합니다. 새로고침과 재진입이 업무를 다시 바꾸지 않아야 합니다.
5. 409는 별도 conflict 노트로 확인합니다. Web이 대상 판 r을 읽어 APPLY를 저장한 뒤, 승인 POST를 Playwright route에서 잠시 대기시킵니다. 그 사이 다른 QA actor가 정상 업무 수정 API로 같은 업무를 r+1로 바꾸고 원 승인 요청을 route.continue()로 그대로 전달합니다. 응답을 바꾸거나 409를 fulfill하지 않습니다. 실제 409 뒤 미승인 상태·변경되지 않은 나머지 승격 결과·사용자 초안을 보존하고, 최신 업무/검토본을 다시 읽어 넘기기로 회복한 뒤 검토 완료할 수 있어야 합니다. 요청을 대기시키기 전에 Web이 최신 판을 감지해 승인을 막았다면 그 결과는 선제 차단이며 실제 409 검증과 구분합니다.
6. 같은 업무의 복수 APPLY는 UI가 승인 전에 막는지 확인합니다. 서버의 중복 APPLY 409 트랜잭션 검사는 서버 소유자가 별도 수행하며 UI 방어를 해제하지 않습니다. 기존 APPLIED seed는 선택을 바꿀 수 없고 완료 때 재적용하지 않는 것도 확인합니다.

GET·PATCH·승인 응답과 전후 업무 판, 화면 캡처, 실제 요청 수만 결과에 남깁니다. 승인 완료와 경합 수정은 허용된 QA 데이터에만 적용하며, 매 실행 전 서버 소유자가 seed를 새로 만듭니다. 환경·권한·seed가 준비되지 않은 상태를 통과로 기록하지 않습니다.
