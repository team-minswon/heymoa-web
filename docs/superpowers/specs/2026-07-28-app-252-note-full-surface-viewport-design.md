# 노트 full 면을 뷰포트에 못박는 설계 (APP-252)

## 배경

노트를 full로 열고 아래로 스크롤하면 회의 면이 끊기고 그 아래로 뒤에 깔린 노트 목록이 보였다.

원인은 **회의 면의 높이가 아니라 그 면을 담는 셸 컨테이너**다. `WorkspaceRouteLayout`이
full 모드에서도 `WorkspacePage`를 계속 마운트해 두는데, `ShellMain`이 `h-full`이라 그 목록
길이를 따라 늘어난다. 목록이 화면보다 길어지면 컨테이너가 뷰포트를 넘고, 그 위에 `absolute`로
앉는 회의 면은 `100svh - 64`만큼만 덮어 아래가 뚫린다.

실측 (1400×760, 목 시드 10개):

|                | 값                        |
| -------------- | ------------------------- |
| 뷰포트         | 760                       |
| 셸 컨테이너    | 1165.7                    |
| 회의 면        | 696 (top 64 → bottom 760) |
| 아래 뚫리는 띠 | 405.7                     |

## 증상 둘이 한 뿌리다

APP-211이 이 면을 `bottom-0`에서 `h-[calc(100svh-4rem)]`로 바꾼 이유가 코드 주석에 남아 있다 —
`bottom-0`이면 회의 면도 컨테이너를 따라 늘어나 레코더 독과 챗 입력창이 화면 밖으로 밀린다.
재현하면 면 높이 1101.7에 독이 y=1165, 뷰포트 밖이다.

컨테이너가 뷰포트에 안 묶인 채로는 `bottom-0`이면 독이 밀리고 고정 높이면 아래가 뚫린다.
**면의 높이를 어떻게 잡아도 하나는 깨진다.** 그래서 컨테이너를 고친다.

## 목표

- 노트 full 면이 상단바 아래 화면 바닥까지 덮는다.
- 목록이 아무리 길어도 문서가 스크롤되지 않는다.
- 레코더 독·챗 입력창이 화면 안에 남는다.

## 제외 범위

- side(시트) 경로 — 이미 `fixed` 오버레이라 이 문제를 타지 않는다.
- `WorkspaceRouteSkeleton`의 `min-h-svh` — 셸이 아직 없을 때의 fallback이고 행 수가 고정이라
  문서를 넘기지 않는다.
- 목록을 언마운트해 컨테이너를 줄이는 방향 — 셸을 route `layout`에 두는 구조(배경 목록 유지)를
  바꾸는 일이고, 돌아올 때 목록을 다시 받아야 한다.

## 핵심 결정

### 1. 셸 컨테이너를 `h-svh`로

`ShellMain`의 `h-full`은 `SidebarInset`을 거쳐 결국 콘텐츠 높이로 풀린다. `h-svh`로 못박으면
그 안의 무엇도 컨테이너를 늘리지 못한다. 회의 면의 기준 상자가 항상 뷰포트다.

`dvh`가 아니라 `svh`다 — 모바일에서 주소창이 접힐 때 컨테이너가 리사이즈되며 목록이 튀는 것보다
바닥에 여백이 잠깐 남는 편이 낫다. 회의 면이 쓰던 단위도 `svh`였다.

### 2. 목록은 자기 안에서 스크롤한다

1번만 하면 긴 목록이 `overflow-hidden`에 잘려 아예 닿지 못한다. 지금 목록은 문서 스크롤에
얹혀 있으므로 스크롤 주체를 옮겨야 한다.

바깥 `section`이 `flex-1 min-h-0 overflow-y-auto`로 스크롤을 갖고, 안쪽에 `mx-auto max-w-4xl`
박스를 하나 둔다. **바깥을 전체 폭으로 두는 이유는 스크롤바 자리다** — 콘텐츠 폭(896)에
스크롤바가 뜨면 본문 한가운데에 줄이 생긴다.

장식 블롭은 안쪽 박스 안에 남긴다. 바깥으로 올리면 `-right-24`의 기준이 화면 폭이 되어 밖으로
나가고, 바깥에 클리핑을 다시 넣으면 APP-226이 고친 이음선이 돌아온다.

바깥에 `overflow-x-hidden`을 함께 준다. `overflow-y`만 주면 계산된 `overflow-x`가 `auto`가 되어
본문이 좁을 때 블롭의 96px이 가로 스크롤이 된다(뷰포트 900에서 `scrollLeft` 96 실측). 자르는
자리는 메인 컬럼 끝이라 이음선은 여전히 안 생긴다 — 셸이 `overflow-hidden`으로 하던 일을 한 칸
안쪽에서 그대로 한다.

### 3. 회의 면은 `bottom-0`으로 되돌린다

컨테이너가 뷰포트에 묶였으므로 `top-16` + `bottom-0`이 곧 상단바 아래 전부다. 상단바 높이
64를 `calc(100svh-4rem)`으로 한 번 더 적으면 CHROME SPEC이 바뀔 때 조용히 어긋난다.

## 검증

jsdom은 레이아웃을 계산하지 않아 vitest로는 못 잡는다. e2e에 기하 단언 하나를 둔다 —
노트 full 경로에서 `document.scrollHeight === clientHeight`이고 면의 bottom이 뷰포트 높이와
같다. 목 시드 10개가 "목록이 화면보다 길다"는 조건을 만든다.

수정 후 실측:

|                   | 전          | 후                       |
| ----------------- | ----------- | ------------------------ |
| 셸 컨테이너       | 1165.7      | 760 (= 뷰포트)           |
| 아래 뚫리는 띠    | 405.7       | 0                        |
| 문서 scrollHeight | 1165        | 760                      |
| 목록 스크롤       | 문서에 얹힘 | client 695 / scroll 1185 |
| 가로 scrollWidth  | 1400        | 1400 (APP-226 그대로)    |
