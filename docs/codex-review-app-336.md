# APP-336 codex 리뷰 기록

`codex exec review --base dev` 4회차. P1은 1회차의 하나뿐이었고 나머지는 전부 P2였다.

## 1회차 — P1 하나, P2 다섯

| 라벨 | 지적 | 처리 |
|---|---|---|
| P1 | 노트가 바뀌어도 `deleteOpen`이 남는다 | 고침 — `NoteActionSlot`을 `noteId`로 키잉 |
| P2 | 단건 캐시가 안 지워진다 | 고침 (2회차에서 범위를 넓힘) |
| P2 | 목록 이동이 `push`라 뒤로가기가 죽은 URL로 간다 | 고침 — `replace` |
| P2 | `mutateAsync` 거절이 미처리로 남는다 | 고침 — `.catch(() => null)` |
| P2 | 좁은 폭에서 상단바가 넘친다 | 고침 — 메뉴를 `sm` 미만에서 감춤 |
| P2 | 목 404 문구가 계약과 다르다 | 고침 |

P1이 제일 날카로웠다. A 노트의 확인창을 연 채 뒤로가기로 캐시된 B 노트에 오면 같은 슬롯이
재사용되어 **B 제목의 창이 열린 채 남고, 그대로 누르면 B가 지워진다.**

## 2회차 — P2 둘, P3 하나

| 라벨 | 지적 | 처리 |
|---|---|---|
| P2 | 전사·요약·공유 채팅 캐시가 각자 키로 살아남는다 | 고침 — noteId를 담은 캐시를 전부 제거 |
| P2 | `invalidateQueries`는 재조회 실패에도 옛 목록을 남긴다 | 고침 — 행을 먼저 빼고 재검증 |
| P3 | 작업용 `.claude/launch.json`이 커밋에 딸려 왔다 | 고침 — 추적 해제 |

두 번째가 미묘하다. `invalidateQueries`는 재조회가 **실패해도 resolve**하고 기존 데이터를
보존한다. 목록 화면도 데이터가 있으면 오류 상태에서 옛 행을 그대로 그리므로, 삭제가 성공했는데
행이 남는 조합이 만들어진다.

## 3회차 — P2 둘

| 라벨 | 지적 | 처리 |
|---|---|---|
| P2 | 후처리 동안 버튼이 다시 열린다 | 고침 — 후처리까지 덮는 잠금 |
| P2 | 개인 챗봇 활성 세션 키가 predicate에 안 걸린다 | 고침 — 키 전체를 문자열로 펴서 판정 |

`deleteNote.isPending`은 DELETE가 끝나면 바로 풀리는데 캐시 정리와 이동이 아직 남아 있다.
그 사이 다시 누르면 지운 노트로 DELETE가 또 나가 **404 오류 토스트와 성공 토스트가 나란히**
뜬다.

## 4회차 — P2 하나, 안 고침

| 라벨 | 지적 | 처리 |
|---|---|---|
| P2 | 개인 챗 메시지 캐시(`/v1/agent-chats/{chatId}/messages`)가 남는다 | **안 고침** |

그 키에는 `noteId`가 없어서 지금 predicate로는 못 잡는다. 잡으려면 삭제 전에 활성 세션을 읽어
`chatId`를 확보해야 하고, 그러면 **삭제 다이얼로그가 agent-chat 내부 키 구조를 알게 된다.**

**남기기로 한 이유**는 노출 경로가 좁아서다 — 종료된 노트에서 개인 챗 턴이 진행 중일 때
상단바로 지우는 경우이고, 삭제 직후 `router.replace`로 목록으로 나가므로 패널이 언마운트된다.
남는 위험은 그 뒤 뒤로가기로 돌아오는 60초 창이다.

활성 세션 키는 이미 지우므로 패널은 재조회를 하게 되고, 메시지만 캐시에서 잠깐 보일 수 있다.

## e2e flake

`shows meeting context and shared chat inside the viewer side panel`이 `--repeat-each 5`에서
간헐 실패한다. **이 브랜치를 stash하고 `dev` 그대로 돌려도 같은 지점에서 깨진다** — 이 작업이
만든 것이 아니다. 챗봇 탭 전환 뒤 공유 챗 컴포저가 5초 안에 안 뜨는 경합이다.
